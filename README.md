# Reelist — Watchlist web app

Frontend for the **REST API class project**. Students build the Watchlist API; this app consumes it.

- **Phase 1:** a CRUD API (built in class). The app works against it as-is.
- **Phase 2:** five extra features the students implement in the API. Each one is turned on in the app's **Lab** panel (flask icon in the header), and the app then starts sending the matching requests.

The API is expected to be an **ASP.NET Core Web API** (controllers with `[ApiController]`). The app reads its default JSON (camelCase) and its default error format (ProblemDetails).

```bash
npm install
cp .env.example .env    # optional: set VITE_API_URL (default http://localhost:3333)
npm run dev
```

The API URL can also be changed at runtime in **Lab → Connection**. Use the `http` URL from the API's `Properties/launchSettings.json`, or set it to a fixed port there. The Lab panel also has:

- **Mock API**: a fake API running in the browser that already implements Phase 1 + Phase 2 and returns the same responses an ASP.NET Core API would. Use it for demos or to compare with the students' API.
- **Requests**: a live log of every request (method, URL, status, time, request/response bodies).

### CORS

The API must allow the frontend's origin. In `Program.cs`:

```csharp
builder.Services.AddCors(o => o.AddDefaultPolicy(p =>
    p.WithOrigins("http://localhost:5173").AllowAnyHeader().AllowAnyMethod()));
// ...
app.UseCors();
```

Also remove `app.UseHttpsRedirection()` (or use the `https` URL in the app). Otherwise requests to the `http` URL get redirected and fail.

## Phase 1: CRUD contract

Resource: `/watchlist` (e.g. `[Route("watchlist")]` on the controller)

```jsonc
// Item (camelCase, the ASP.NET Core default)
{
  "id": 1,                   // int, generated by the API
  "title": "Dune: Part Two", // required
  "type": "movie",           // "movie" | "series", required
  "year": 2024,              // int or null
  "genre": "Sci-Fi",         // string
  "posterUrl": "",           // string (image URL); the app generates a poster when empty
  "notes": "",               // string
  "watched": false,          // bool
  "createdAt": "2026-10-13T12:00:00Z", // optional, set by the API
  "updatedAt": "2026-10-13T12:00:00Z"  // optional, set by the API
}
```

| Method | Path             | Body          | Success                         | Errors |
| ------ | ---------------- | ------------- | ------------------------------- | ------ |
| GET    | `/watchlist`     | –             | `200 Ok(list)`                  | |
| GET    | `/watchlist/{id}`| –             | `200 Ok(item)`                  | `404 NotFound()` |
| POST   | `/watchlist`     | item (no id)  | `201 CreatedAtAction(...)`      | `400` |
| PUT    | `/watchlist/{id}`| full item     | `200 Ok(item)`                  | `400`, `404` |
| DELETE | `/watchlist/{id}`| –             | `204 NoContent()`               | `404` |

### Errors

The app expects ASP.NET Core's **default** error responses. Students don't need to build any custom error format:

- `return NotFound();` → `404` ProblemDetails `{ "title": "Not Found", "status": 404, ... }`. The app shows the `title` (or `detail`, if present).
- Validation errors are returned automatically by `[ApiController]` as `400` **ValidationProblemDetails**:

```json
{
  "type": "https://tools.ietf.org/html/rfc9110#section-15.5.1",
  "title": "One or more validation errors occurred.",
  "status": 400,
  "errors": {
    "Title": ["The Title field is required."],
    "$.year": ["The JSON value could not be converted to System.Nullable`1[System.Int32]. ..."]
  },
  "traceId": "00-..."
}
```

The form shows each message under its field. It matches keys case-insensitively (`Title` → title) and also accepts JSON paths (`$.year` → year). Errors that don't belong to a field, like `"request": ["The request field is required."]`, are listed at the top of the form.

In Phase 1, the **"Mark as watched"** button sends a full `PUT` with the whole object. The "To watch / Watched" tabs filter **on the client**.

## Phase 2: student assignments

Turn each one on in **Lab → Phase 2** once it's done. The full contract, with a C# hint, is also shown inside the app.

| # | Feature | Level | What the API must do |
|---|---------|-------|----------------------|
| 1 | **Search & filters** | Easy | `GET /watchlist?q=&type=&watched=` using `[FromQuery]` params. Filtering moves from the client to the server. |
| 2 | **Partial updates (PATCH)** | Easy | `PATCH /watchlist/{id}` with only the changed fields (e.g. `{ "watched": true }`) → `200` full item. A DTO with nullable properties is enough; no JSON Patch needed. |
| 3 | **Ratings** | Easy | New property `int? Rating` with `[Range(1, 5)]`, accepted on POST/PUT/PATCH. Stars appear on the cards. |
| 4 | **Stats endpoint** | Medium | `[HttpGet("stats")]` → `{ total, watched, unwatched, byType: { movie, series }, averageRating }`, computed with LINQ. |
| 5 | **Server-side validation** | Medium | The form stops validating in the browser. The API must reject bad input using DataAnnotations (`[Required]`, `[StringLength(120)]`, `[AllowedValues("movie","series")]`, `[Range(1888, 2031)]`). `[ApiController]` returns the 400 automatically. |

Suggested discussion points per feature:

- **1:** query strings vs route params, nullable params as "optional filters", building a LINQ query step by step.
- **2:** PUT (replace) vs PATCH (partial). Compare the two in the Requests log.
- **3:** evolving a resource without breaking existing clients (old items have no `rating`).
- **4:** endpoints that aren't plain CRUD; how routing picks `stats` over `{id}`.
- **5:** never trust the client; model binding vs validation errors (`$.year` vs `Year`); ProblemDetails as a standard (RFC 9457).

Ideas for further assignments (not wired into the UI): sorting (`?sort=&order=`), pagination, bulk delete (`DELETE /watchlist?watched=true`), EF Core persistence, auth with per-user lists.
