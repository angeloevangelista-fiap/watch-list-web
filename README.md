# Watchlist web app

Frontend for the **REST API class project**. Students build the Watchlist API; this app consumes it.

- **Phase 1:** a CRUD API (built in class). The app works against it as-is.
- **Phase 2:** four extra features the students implement in the API. Each one is turned on in the app's **Lab** panel (flask icon in the header), and the app then starts sending the matching requests.

The API is expected to be an **ASP.NET Core Web API** (controllers with `[ApiController]`). The app reads its default JSON (camelCase) and its default error format (ProblemDetails).

```bash
npm install
cp .env.example .env    # optional: set VITE_API_URL (default http://localhost:3333)
npm run dev
```

The API URL can also be changed at runtime in **Lab → Connection**. Use the `http` URL from the API's `Properties/launchSettings.json`, or set it to a fixed port there. The Lab panel also has:

- **Mock API**: a fake API running in the browser that already implements Phase 1 + Phase 2 and returns the same responses an ASP.NET Core API would. Use it for demos or to compare with the students' API.
- **Requests**: a live log of every request (method, URL, status, time, request/response bodies).

### CORS

The API must allow the frontend's origin. In `Program.cs`:

```csharp
builder.Services.AddCors(o => o.AddDefaultPolicy(p =>
    p.WithOrigins("http://localhost:5173").AllowAnyHeader().AllowAnyMethod()));
// ...
app.UseCors();
```

Also remove `app.UseHttpsRedirection()` (or use the `https` URL in the app). Otherwise requests to the `http` URL get redirected and fail.

## Phase 1: CRUD contract

Resource: `/api/watchlist` (e.g. `[Route("api/watchlist")]` on the controller). All endpoints live under `{base}/api/`.

```jsonc
// Item (camelCase, the ASP.NET Core default)
{
  "id": 1,                   // int, generated by the API
  "title": "Dune: Part Two", // required, max 120 characters
  "year": 2024,              // int or null, 1888..(current year + 5)
  "genre": "Sci-Fi",         // string
  "posterUrl": "",           // string (image URL); the app generates a poster when empty
  "notes": "",               // string
  "watched": false           // bool
}
```

| Method | Path             | Body          | Success                         | Errors |
| ------ | ---------------- | ------------- | ------------------------------- | ------ |
| GET    | `/api/watchlist`     | –             | `200 Ok(list)`                  | |
| GET    | `/api/watchlist/{id}`| –             | `200 Ok(item)`                  | `404 NotFound()` |
| POST   | `/api/watchlist`     | item (no id)  | `201 CreatedAtAction(...)`      | `400` |
| PUT    | `/api/watchlist/{id}`| full item     | `200 Ok(item)`                  | `400`, `404` |
| DELETE | `/api/watchlist/{id}`| –             | `204 NoContent()`               | `404` |

### Errors

The app expects ASP.NET Core's **default** error responses. Students don't need to build any custom error format:

- `return NotFound();` → `404` ProblemDetails `{ "title": "Not Found", "status": 404, ... }`. The app shows the `title` (or `detail`, if present).
- Validation errors are returned automatically by `[ApiController]` as `400` **ValidationProblemDetails**:

```json
{
  "type": "https://tools.ietf.org/html/rfc9110#section-15.5.1",
  "title": "One or more validation errors occurred.",
  "status": 400,
  "errors": {
    "Title": ["The Title field is required."],
    "$.year": ["The JSON value could not be converted to System.Nullable`1[System.Int32]. ..."]
  },
  "traceId": "00-..."
}
```

The app does **no validation of its own**: the form sends exactly what was typed (e.g. `"year": "abc"`), so the API is the one that has to reject bad input. When it does, the form shows the status, the `title`, and every entry of `errors` as the API sent it. Each message also appears under its field. Keys are matched case-insensitively (`Title` → title), and JSON paths are understood too (`$.year` → year).

In Phase 1, the **"Mark as watched"** button sends a full `PUT` with the whole object. The "To watch / Watched" tabs filter **on the client**.

## Phase 2: student assignments

Turn each one on in **Lab → Phase 2** once it's done. The full contract is also shown inside the app.

| # | Feature | What the API must do |
|---|---------|----------------------|
| 1 | **Search & filters** | `GET /api/watchlist?q=&watched=`. Filtering moves from the client to the server. |
| 2 | **Partial updates (PATCH)** | `PATCH /api/watchlist/{id}` with only the changed fields (e.g. `{ "watched": true }`) → `200` full item. Fields not sent stay unchanged. |
| 3 | **Ratings** | New field `rating`: integer 1–5 or `null`, accepted on POST/PUT/PATCH. Stars appear on the cards. |
| 4 | **Stats endpoint** | `GET /api/watchlist/stats` → `{ total, watched, unwatched, averageRating }`. |

Suggested discussion points per feature (for the teacher):

- **1:** query strings vs route params; optional filters.
- **2:** PUT (replace) vs PATCH (partial). Compare the two in the Requests log.
- **3:** evolving a resource without breaking existing clients (old items have no `rating`).
- **4:** endpoints that aren't plain CRUD (computed resources).

Ideas for further assignments (not wired into the UI): sorting (`?sort=&order=`), pagination, bulk delete (`DELETE /api/watchlist?watched=true`), EF Core persistence, auth with per-user lists.

## Project structure

```
src/
  features.js         Phase 2 catalog (titles and contracts shown in the Lab)
  settings.jsx        API URL, mock toggle, feature flags (saved in localStorage)
  api/client.js       fetch wrapper, ProblemDetails parsing, request log
  api/watchlist.js    endpoint functions (only sends params for enabled features)
  contract.js         builds the active API contract (Lab → API contract)
  api/mock.js         in-browser mock that answers like an ASP.NET Core API
  components/         UI (cards, form, Lab panel, stats, …)
```
